# 胶囊台阶实验 · 结论与对照

本文件记录两套台阶处理方案在**同一个真实胶囊**上的对照实验、斜坡 / 顶面净空 / 大步长的处理结论，以及尚未验证的假设。所有穿透量与可达位移均由代码复算，复算命令与数据校验和见文末；本文不手写、不估算任何测量数字。

- 求解器实现：`src/sim/step-schemes.js`
- 控制器接入：`src/sim/character.js`（`step()` 的阶段 B）
- 实验运行器（数据来源）：`src/experiments/steps.js`
- 视窗交互验证：`scripts/e2e-viewport.js`
- 机器生成数据表：`experiments/step-results.{json,md}`（由运行器生成，已 gitignore）

## 1. 两套方案的定义

两套方案驱动的是同一个 `CharacterController`、同一套 `sweepCapsule()` 距离查询扫描，差别只在台阶阶段的运动组织方式。两者都**不是**把角色位置直接贴到台阶顶端：每一次姿态变化都是一次真实的胶囊扫掠，并且沿扫掠经过的空间逐段做穿透检查。

| 方案 | id | 运动顺序 | 关键约束 |
| --- | --- | --- | --- |
| 先水平扫描再抬升 | `horizontal-first` | 先在当前高度推完整水平请求 → 撞到立面停住 → 再按实测抬升量抬升 → 抬升态前移 → 落脚 | 立面阻挡被记为 `riser-block`；抬升量 = 实测 rise + 球心下垂 sag，并被净空预算钳制；前移不超过一个半径 |
| 受限多候选运动求解 | `constrained-candidates` | 同时构造三条有界候选路径（抬升优先 / 对角切角 / 贴坡爬升），逐条过门控，首个可行者胜出 | 每条候选的每个相位都过扫掠截断、行程不足、路径穿透、净空四道门；选中原因可解释 |

旧样例 `lift-first`（`assessStep()`，整体抬升到台阶上限再前移）作为对照基线保留，重放检查仍在该方案下跑完全程。

### 为什么必须计算球心下垂量

胶囊底部是半径 r 的半球。当轴与立面还有水平间隙 g 时，球面要越过棱边，轴必须额外抬高 `sag = r - sqrt(r² - g²)`。若抬升只按立面高度 rise 给，求解器会在"看起来够高"时把球面刮进棱边。两个新求解器都把 sag 计入抬升需求，因此实验中路径穿透恒为 0，而不是靠末端解穿回拉。

## 2. 数据如何复算（防伪报）

穿透量在 `penetrationCrossCheck()` 中走三条相互独立的路径，对同一份几何复算：

- **A 终点查询**：对最终姿态做 `maxPenetration()`，即 UI 显示的末端穿透。
- **C 重建控制器再查询**：用相同配置新建控制器、放到同一姿态再查一次。A 与 C 必须**逐位相等**。
- **B 沿真实路径每 2 cm 子采样**：沿求解器各相位扫掠拼成的**真实折线**（抬升 / 前移 / 下落分别取 from→to），每 2 cm 插一个姿态做独立距离查询，取整条路径的最大穿透。起点 t=0 排除，零长度段跳过，因此既不会把预存重叠算成运动穿透，也不会用帧端点弦线穿过台阶虚构穿透。B 必须 ≥ A，表中报告 B。

可达位移 = 末端与起点的水平距离；被拒绝的求解器不提交位置，因此其可达位移为 0。

## 4. 三个专题结论

### 4.1 斜坡（ramp）

斜坡**不**走台阶通道。`measureRiser()` 用 `TREAD_NORMAL_Y = 0.94` 门控踏面法线：24° 坡的法线 y 分量为 cos24° ≈ 0.914，被排除在台阶之外，两个求解器对斜坡一律返回 `no-tread`（一次性表）。坡面改由阶段 A 的 `projectOnSupport()` 支撑面投影处理。

驱动实验（ramp-24 场景，持续行进 1.3 m）验证了这一点：25 次台阶尝试 0 次接受，支撑面最终命中 `ramp24`、地面角稳定 24.00°，垂直增益 0.455 m 且不超过"水平位移 × tan24°"的几何上界，路径穿透为 0。

视窗 E2E 还暴露并修复了一个真实缺陷：旧的触发判定把坡面投影后的三维位移与纯水平请求比较，导致在 16° 上坡上每帧误触发台阶、产生毫米级假 `step-up`。修复后触发比较改为三维投影长度，并规定 rise ≤ 1 cm 的成功不计入 step-up；E2E 的逐帧 trace 现在在整个坡段 `stepUp=false`、坡角稳定 16°，而真实 0.22 m 台阶的登阶计数不变。

### 4.2 顶面净空（headroom）

净空不是单点射线，而是沿胶囊将要占据的整个水平范围（轴 + 前移 reach）每 5 cm 采样最低顶面的**有符号间隙**（`headroomBudget()`）。只统计顶面严格高于当前顶点的盒体，地面 / 立面被排除；间隙为负表示顶点已侵入，直接把允许抬升钳到 0。

- 矮顶台阶（顶面下沿 2.10 m）：满抬升 0.32 m 后顶点 2.02 m，剩 8 cm 净空，抬升被净空预算收紧但仍足够越过 riser，两方案均成功且零穿透。
- 极矮顶（顶面下沿 1.90 m）：最小 0.22 m 抬升就会让顶点（1.92 m）侵入 2 cm，两方案都拒绝、可达位移为 0、零穿透。"成功嵌入顶面"不是一个可选项。

### 4.3 大步长限制（large stride）

距离查询扫掠的迭代有硬上限（`maxSweepIterations`，内部再钳到至少 4），超长单帧位移可能在迭代预算耗尽时被截断，`sweepCapsule()` 用 `truncated` 标志显式报告而不是假装走完。

0.90 m 单帧请求最清楚地体现两方案差异：

- **horizontal-first 只走到 0.370 m**：水平扫掠先撞上立面、又受迭代上限截断，请求的大步被立面和预算共同限制。
- **constrained-candidates 走满 0.900 m**：候选路径把抬升与前移组织成有界相位，不依赖"先水平撞墙"这一步，因此在同样零穿透下保留了完整请求位移。

这正是两套方案的核心权衡：水平优先更"保守、可解释地停在障碍前"，多候选在受限预算内更能保住大步长的可达位移，但代价是候选构造与门控更复杂。

## 5. 待验证假设（不作为已证结论）

以下是设计中采用、但当前实验尚未专门证伪的假设，单列以便后续补实验，不在结论中当作既成事实：

1. **sag 系数的普适性**：当前 sag 公式按球面绕单条水平棱边推导。对凹角、双棱边同时贴近或非轴对齐立面，该下垂量是否仍充分，未做专门场景验证。
2. **5 cm 净空采样密度足够**：`headroomBudget()` 每 5 cm 采一个顶面间隙。若出现比采样间隔更窄的下垂梁或锯齿顶面，可能漏检；未构造此类薄特征场景。
3. **2 cm 穿透门限的工程合理性**：实验以 2 mm 子采样、2 mm 违例门限判"无显著穿透"。该阈值是工程容差而非物理零，在更高速率或更薄碰撞体下是否仍合适未验证。
4. **多候选顺序即最优**：多候选方案固定按 抬升优先 → 对角切角 → 贴坡爬升 取首个可行者。这保证可解释，但未证明在净能耗、姿态平稳或落点质量上最优。
5. **斜坡 0.94 法线门限的边界**：该门控能区分 24° 坡与水平踏面，但对 18°–20° 之间的缓坡与极矮台阶组合，是否会误分类，缺少边界角度扫描实验。
6. **多平面并发台阶**：实验台阶都是单一正向立面。角色在墙角斜向同时逼近两个台阶面时，候选路径与多平面裁剪的交互未单独验证。

## 6. 视窗交互证据（CLI 不能替代）

`npm run e2e` 启动真实 Vite dev server，用本地库（`scripts/fetch-browser-libs.sh` 提取到 `local-libs/`）启动 headless Chromium，通过 `window.__capsuleDemo` 钩子驱动**渲染中的同一个控制器**，共 25 项断言，覆盖：

- 平地按住 W 的真实水平位移、支撑接触点高度、零穿透；
- 16° 上坡的支撑面投影、坡角与"无台阶抬升"逐帧 trace；
- 两套实验方案分别驱动同一胶囊登 4 级台阶，登阶中途接触位置落在 `stair-*` 碰撞体上、路径与端点穿透均为 0；
- 0.38 m 超限高台的拒绝计数、零嵌入，以及视窗内**异常横幅**对地面运动 / 台阶异常的可见标记；
- 半径滑杆实时改变真实碰撞体并保持无穿透；
- 暂停态可见且暂停时输入不产生位移；
- 全程无页面 / 控制台错误。

截图与 JSON 报告写入 `experiments/e2e/`（gitignore）。运行状态在视窗左上 HUD 实时显示，异常在视窗底部红色横幅累计标记。
